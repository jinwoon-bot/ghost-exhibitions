# ⑤ 〈화면 속에만 있는 사람〉 실시간 그림자판

## 기존판 분석

| 부분 | 기존 고개 반응판 |
| --- | --- |
| 실행과 배포 | `site/works/only-on-screen/index.html`. GitHub Pages의 통합 페이지에서 작품별로 진입하는 정적 웹. |
| 웹캠 | `src/camera.mjs`의 브라우저 `getUserMedia`, 카메라 목록, 프레임 수신과 연결 끊김 감시. |
| 인식과 분리 | `vision-worker.js`에서 MediaPipe Pose Landmarker Lite로 최대 3개 자세를 받고 Face Landmarker도 사용합니다. 여러 인물의 분할 마스크를 픽셀 최댓값으로 합쳐 가림에 사용합니다. |
| 관객 선택 | `src/tracking.mjs`의 대표 관객 선택과 `src/experience.mjs`의 고개 회전 기반 진행. |
| 효과와 에셋 | `src/compositor.mjs`에서 Canvas 2D로 흑백 거울과 사전 제작 몽달 WebM, 전경 가림을 합성합니다. 두 WebM은 약 1.8MiB입니다. |
| 당시 성능 기록 | 기존 프로젝트의 `docs/VALIDATION.md`에 따르면 800×600 GPU 샘플 시험에서 브라우저 약 58.79 rAF/s, AI 평균 168.53ms, p95 214.6ms, AI 결과 2,321회, 오류 0건이었습니다. 초기 CPU 시험은 약 37.13 rAF/s를 기록했습니다. 서로 다른 인원의 별도 실루엣과 실제 센서 지연을 잰 기록은 없습니다. |

기존 파일은 그대로 유지했습니다. 새 작품은 `site/works/only-on-screen-live/`에 있고, 통합 메뉴에서 이전 고개 반응판에도 접근할 수 있습니다.

## 새 합성

- `app.mjs`는 카메라와 렌더링을 관리합니다. 원본 영상의 한 프레임을 분석에 보내고 그 프레임과 같은 시점의 마스크로 합성합니다. 분석 작업은 동시에 하나만 진행합니다.
- `segment-worker.js`와 `masks.mjs`는 공용 MediaPipe 모델의 사람별 마스크를 유지합니다. 겹치는 픽셀은 신뢰도와 자세 영역을 고려해 한 사람에게만 배정합니다. 불확실한 가장자리를 부드럽게 하고, 확신도가 높은 손 윤곽은 유지합니다. 어두운 입력은 추론용 사본에서 밝기를 조정합니다.
- `tracks.mjs`는 몸통 위치, 속도, 크기로 짧게 추적 번호를 유지합니다. 새 프레임에서 관측되지 않은 몸은 화면에 남기지 않습니다. 짧은 가림 중에는 좌표 기반 추적 정보만 남습니다.
- `stage.mjs`는 사람별로 같은 발밑 지점에서 각도, 폭, 길이, 번짐과 농도가 다른 2~4개 먹빛 그림자를 계산합니다. 현재 인물을 마지막에 겹치며, 반투명 경계에 들어온 배경색을 재료색으로 줄입니다. 한지 배경의 정지 WebP는 약 252KiB이며 ImageGen으로 제작했습니다. 배경은 차가운 먹빛의 낡은 한지, 약한 중심광, 글자와 인물 없는 벽으로 제작했습니다. 움직이는 그림자 소스로 쓰이는 사전 제작 영상은 없습니다.
- 기본 음향은 꺼져 있습니다. 운영자가 켜면 기존의 낮은 공간음을 브라우저에서 합성합니다.
- 카메라 영상, 실루엣, 추적 좌표는 브라우저 메모리에서 처리합니다. 서버 전송, 파일 기록, 얼굴 식별은 구현하지 않았습니다. 브라우저에는 장치와 작품 설정만 저장됩니다.

## 전시장 운영

1. 최신 Chrome에서 공개 HTTPS 주소를 열고 **카메라로 시작**을 누릅니다. 주소창의 카메라 사용 요청을 허용합니다.
2. 카메라에 세 사람의 머리부터 발까지 모두 들어오게 맞춥니다. 운영 설정에서 카메라를 고른 뒤 **카메라 다시 연결**을 누릅니다. `D`로 운영 화면을 열고 닫을 수 있습니다.
3. 성능은 **자동**으로 시작합니다. 먼저 해상도와 분석 주기를 낮춰 세 명을 유지하고, 부담이 지속될 때 두 명 또는 한 명으로 내려갑니다. 세 명 시험 시 **높음**을 선택하면 인원 상한이 세 명으로 고정됩니다. **GPU 사용 가능 시**는 초기화 또는 분석 오류 발생 시 CPU로 전환합니다.
4. 운영 설정에서 카메라 전체 배경 표시, 좌우 반전, 그림자 수·강도·기울기, 색감, 윤곽 기준과 공간음을 조절합니다. **화면만 표시**로 패널을 닫고 `F`로 전체화면을 켭니다. `R`은 현재 추적 상태를 지웁니다.
5. 권한이 거부되면 Chrome 주소창의 사이트 설정을 확인합니다. 카메라가 끊기면 USB나 다른 앱의 사용 여부를 확인하고 **카메라 다시 연결**을 누릅니다. 모델 경로 또는 성능 문제는 운영 상태에 표시됩니다.
6. 카메라 없이 **샘플 영상 시연**을 선택할 수 있습니다. 기본 세 사람 배치 영상은 TensorFlow 공식 샘플의 동일 출연자를 세 번 배치한 시험 입력입니다. 운영 설정에서 이 PC의 다른 영상을 열 수도 있습니다. 로컬에서 실행할 경우 `node tools/serve.mjs`로 HTTP 서버를 열어 접속합니다.

## 검증 범위

`node --test tools/test-screen-live.mjs`는 마스크 픽셀의 단일 소유, 각 손 위치의 독립성, 접촉점, 불확실한 경계 보정, 순서 변경, 좌표 교차 및 퇴장·재등장에 대한 자동 검사 6개를 실행합니다. 공개 페이지 시험에서 배경의 작은 오인식이 발 기준점을 옮기는 사례를 확인했습니다. 관절 범위 주변으로 마스크를 제한하고 발 위치를 함께 고려하도록 수정했습니다.

- **브라우저 입력 시험**. 공식 영상 세 영역을 별도로 조작한 가상 카메라로 실제 추론을 실행했습니다. 세 마스크와 세 추적 번호가 나왔고, 두 구역의 손목 높이는 화면 높이 기준 약 13%·23% 달라졌습니다. 나머지 구역은 0.6% 이내였습니다. 입력을 3 → 2 → 1 → 0명으로 줄이자 남은 인물의 추적 번호가 유지됐으며, 정상 조명으로 돌아오면 세 명을 다시 분리했습니다. 카메라 권한 거부 안내, 영상 끊김 감지, 끊긴 뒤 샘플 시작을 확인했습니다.
- **어두운 입력 시험**. 평균 밝기 약 56/255로 낮춘 시험에서 세 위치 중 한 사람만 검출됐습니다. 어두운 환경에서 세 명의 분할을 보장하기 어렵습니다.
- **120초 연속 합성**. Windows의 Chrome, 960×720 가상 입력, CPU의 자동 성능 모드에서 30개 표본을 비교했습니다. 새 마스크를 합성한 속도는 5.37~6.65회/초, 캡처부터 분석 결과까지의 이동평균은 146.64~182.94ms, 마스크 합성 준비 2.07~2.80ms였습니다. 마지막 누적 수치는 카메라 프레임 3,877개와 분석 결과 817개였으며 시작·전환 시험 값도 포함합니다. 자동 모드는 3명 설정에서 2명 설정으로 내려갔습니다. 브라우저 화면 콜백 속도는 118.03~120.04회/초였으며 실제 그림자 갱신 속도는 위의 합성 수치를 참고합니다. 표시된 JS 힙 1.85~8.45MiB는 Chrome의 참고값이며 WASM·GPU 메모리를 포함하지 않습니다. 측정한 환경에서 목표 30 FPS의 실시간 마스크 갱신에 도달하지 못했습니다.
- **GPU 장애 대응**. Chrome 시험에서 GPU 초기화 뒤 첫 분석 응답이 멈춘 경우, 5초 감시 뒤 CPU로 전환해 세 마스크를 다시 생성했습니다. GPU가 응답한 별도 헤드리스 시험에서도 세 자리 중 두 자리만 지속 감지한 경우가 있었습니다. CPU를 기본값으로 두었습니다.
- **실제 웹캠**. Windows Chrome에서 내장 카메라 1280×720 입력으로 관객 한 사람의 팔 움직임을 확인했습니다. 16회 읽은 운영 수치에서 관객 ID와 그림자 수 3개가 유지됐고, 화면 안 손목 높이는 정규화 좌표 약 0.93에서 0.56까지 움직였습니다. 같은 구간의 새 합성 속도는 약 8.71~10.01회/초였습니다. 한 사람이 가까이 선 시험이며 카메라 이미지나 영상은 저장하지 않았습니다.

서로 다른 세 사람이 실제로 팔을 들거나 가까이 교차할 때의 인식, 실제 고개 돌림·숙임·퇴장, 현장 조도 및 전시 시간 전체 안정성은 추가 검증이 필요합니다. 완전히 가려진 관객의 윤곽은 복원할 수 없습니다. 머리카락과 손가락처럼 작은 부분은 카메라 해상도와 조명, 모델의 분할 결과에 따라 단순화됩니다.
